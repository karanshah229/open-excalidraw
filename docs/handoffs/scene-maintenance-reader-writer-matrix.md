# Scene maintenance reader/writer matrix

This inventory records the current `boardScenes/{boardId}` scene protocol for ADR 007 Phase 0. “Pinned” means a server-created durable `readerPins` record protects the exact immutable revision while its pages/chunks are read. “Fenced” means the operation serializes against the board’s `maintenance/control` admission epoch. Source locations are repository-relative and line numbers refer to this worktree at the time of this audit.

## Legacy-client and Phase 0 implications

- Current clients identify the protocol version in pin and upload callables; server callables reject missing/unsupported versions, and staged uploads persist the version. This fences scene writers that use the supported callables.
- Firestore rules permit authorized reads only of the board head metadata. A cached legacy client cannot read revisions, pages, versions, uploads or chunks and cannot use the old direct-write path. Current clients require protocol version 1 for both upload and pin-bound read callables. Emulator tests verify direct reads fail and callable reads carry pin/revision/protocol fields.
- RTDB collaboration remains a separate ingress for element deltas and presence. The abandoned-room Function is the only path found that folds those deltas into Firestore scenes. RTDB writes do not transact on the Firestore admission epoch, so future generation reset, tombstone compaction, or deletion policies need explicit RTDB fencing and stale-room recovery (ADR 007 Phase 6).
- The dry-run includes stored/reachable/candidate byte counts and can persist a sanitized snapshot to a new operator-selected JSON file; it is point-in-time evidence, not ongoing telemetry. The classified fixture corpus and this source-backed provenance matrix now exist. A valid-board CLI test confirms a complete report, reachable/stored byte counts and no deletion authorization. No historical-version writer/reader lifecycle is implemented.

## Current phase gate status

- Phase 0: implementation evidence exists for classified fixtures, dry-run byte reporting/persistence and protocol metadata. The corpus/planner/backend tests pass; complete phase exit still requires a valid-board dry-run test and reviewing the saved operator report format.
- Phase 1: writers and current readers participate in protocol/fencing. Firestore rules deny direct payload reads for cached legacy bundles; current browser payload reads use bounded, pin-verified callables. Backend and browser emulator tests cover caller ownership, pin lifetime, exact revision/page references and direct-read denial.
- Phase 2: orphan-only quarantine/collection has independent reachability and crash/recovery coverage with persisted pause/retry metrics. It is internal, unexported and unscheduled. No production canary or destructive invocation has occurred.

## Audit boundary

The search covered application TypeScript, Functions TypeScript, Firestore rules, RTDB rules, and the maintenance scripts for `boardScenes`, revision/page/chunk collections, upload callables, `loadSceneRevision`, `checkpointScene`, and RTDB compaction. Test fixtures and the dry-run tool may use Admin SDK access but are not production user readers/writers. This inventory is source-based; it is not integration-test evidence that every deployed client version or production trigger follows the matrix.
