# Firebase no-cost allowances and board limits

Verified against official documentation on 2026-10-02 (client date). This records current public allowances; it does not establish actual production usage or costs.

## Key distinction

Firebase has no built-in free-tier allowance per board or per end user. Free usage is shared across the application/project, or across its billing account/organization for some Google Cloud products. On Blaze, exceeding a no-cost allowance generally incurs charges. A board-size alert therefore needs an application policy; it cannot promise that the whole project remains free.

The immediate board-specific constraint is Firestore's **1 MiB (1,048,576 bytes) maximum document size**, a hard limit on paid plans too. Field values have a 1 MiB minus 89 bytes limit; nested arrays/maps have a depth limit of 20. [Firestore quotas](https://firebase.google.com/docs/firestore/quotas)

**Documentation discrepancy:** the current [Firebase pricing overview](https://firebase.google.com/pricing) lists **360 MB/day** no-cost transfer for Blaze Hosting and Realtime Database, while their detailed billing pages above state **10 GB/month**. These are different enforcement windows, despite being presented as approximately equivalent. Confirm the project's applicable billing SKU/window before implementing exact free-quota counters; do not silently substitute one for the other.

**Functions generation matters:** the Firebase overview's 400,000 GB-seconds / 200,000 CPU-seconds / 5 GB networking values correspond to the older functions offering; the Google Cloud functions pricing page explicitly routes gen2 to Cloud Run pricing. Do not use the legacy values for this application's gen2 functions.

## Other hard limits and cost multipliers

- RTDB supports 200,000 simultaneous connections per database on Blaze; **100 is the Spark limit**, not a free connection threshold on Blaze. SDK writes are limited to 16 MB per request, string values to 10 MB, and individual responses to 256 MB. [RTDB limits](https://firebase.google.com/docs/database/usage/limits)
- Firestore listeners incur reads when documents are added/updated, and reconnects can rerun the query. Security-rule dependent document reads also count. Stored metadata and indexes consume storage alongside payload data. Board bytes alone do not determine read/write or egress usage. [Firestore billing](https://firebase.google.com/docs/firestore/pricing)
- Firestore document size includes its path, field names, values and overhead. String sizes use UTF-8 bytes plus one, so JSON string length is only an estimate. Index storage is additionally relevant to total database storage. [Size calculations](https://firebase.google.com/docs/firestore/storage-size)
- App Check creates a reCAPTCHA assessment on token refresh. Default TTL is one hour with refresh around half-TTL, so sessions and time spent in the app drive this usage. [App Check provider pricing](https://firebase.google.com/docs/app-check/web/recaptcha-enterprise-provider)
- Auth account creation is limited to 100 new accounts/hour per IP, with abuse protections; this is a service limit rather than a board-size budget. [Auth limits](https://firebase.google.com/docs/auth/limits)
- TTL deletes, PITR, backups, restores and clones have no Firestore free usage. Budget alerts notify about spend and do not cap charges. [Firestore quotas and budgets](https://firebase.google.com/docs/firestore/quotas)

## Deployment facts to verify before selecting thresholds

Confirm the effective image bucket name and location, Identity Platform upgrade state, App Check provider/enforcement, total project usage, function billing configuration, and other projects on the same billing account/organization. A configured bucket name does not establish that the bucket exists or qualifies for free regional storage.

## Implications for the next alert discussion

**Resource recheck on 2026-10-03:** both application image buckets now exist: `open-excalidraw-dev-2.firebasestorage.app` and `open-excalidraw-b2ab4.firebasestorage.app`, both in `ASIA-SOUTH1` (Mumbai). The missing-bucket observation above describes the earlier inventory, not current state. Bucket existence/location was verified with `gcloud storage buckets list`; frontend configuration, CORS and deployed Storage rules were not retested in this recheck. Mumbai does not qualify for the US-only Standard storage/operation free allowance for new buckets. [Storage free-tier locations](https://firebase.google.com/docs/storage/faqs-storage-changes-announced-sept-2024)

**Live dev recheck on 2026-10-03:** the authenticated Firestore API reports dev `open-excalidraw-dev-2` in `nam5`, while its existing deployed callable/RTDB functions run in `us-central1`. The dev Storage bucket remains in `ASIA-SOUTH1`. The production location table above must not be applied to dev. Live freemium callables were added in `us-central1` without replacing other worktrees' existing dev functions or rules.

- **Saved board document size:** Full scenes occupy single Firestore documents. Private, shared and recovery-history copies each must fit the hard 1 MiB limit. Measure the transformed cloud document, including metadata, nested-array encoding and image references. External image bytes do not belong in this metric.
- **Image size:** Cloud sync rejects images at or above **10 MiB** (`scene-assets.ts` and `storage.rules`). This is an application limit, not a Firebase free-tier limit. Sharing can create a second copy of private image assets.
- **Collaboration element size:** The app caps serialized elements at roughly 256 KiB. The check actually uses JavaScript string length, and RTDB rules require fewer than 262,144 characters, so it is not a reliable byte counter. Oversized elements log a warning and skip broadcast rather than showing a user alert.
- **Existing displayed file size:** `board-editor.tsx:getSceneSize` serializes the local scene with embedded image data URLs and full current app state. It measures neither the cloud Firestore document nor raw image-storage bytes, so it must not directly drive a Firestore-limit warning.
- **Activity affects cost:** Saves debounce for 450 ms; workspace board writes have a 1-second minimum interval, but shared scene writes are separate. Listener fan-out increases reads/downloads; cursors can broadcast about every 33 ms; every shared-document write invokes the access mirror. The compactor waits 30 seconds for an empty room before recovery, consuming function execution time.
- **Retained data matters:** Deleted elements/files remain for undo, board deletion marks a board inactive, and recovery writes append full-scene history documents. No image garbage collection or history retention cleanup was found. Visible element count and active-board count understate retained data.
- **No natural free board-count limit:** Per-board size, per-user storage, and project-wide operations/traffic need separate policies. Board warnings can prevent save failures and discourage heavy usage, but cannot guarantee zero total charges on Blaze.

No alert UI, rules, quotas or deployment configuration were changed in this investigation.
